# The core updates by three-way merge

A project is generated from the starter once, and from then on the two drift: the starter gains fixes to its components, lint rules, scripts and agent guide, and the project has no way to take them. Add-ons already solved this for themselves (`pnpm addon update`, `docs/adr/0009`); `pnpm starter update` does it for everything else, the core. `starter.lock.json` records the starter commit the project last matched. For each core file the starter changed since that commit: a file nobody touched in the project is replaced, a file both sides changed is merged line by line (`git merge-file`, with the recorded commit's copy as the common ancestor), and a file that can't be merged cleanly is left untouched with the starter's version beside it as `<file>.starter-update` for a person to merge. New files are added, files the starter dropped are removed only when unchanged, and a file the project deleted stays deleted. `pnpm starter status` shows how far behind a project is and what an update would do, changing nothing. The core is every file tracked in the starter except what an add-on installs (the `target`s in each `add-ons/*/addon.json`, which `pnpm addon update` owns) and the paths the project owns, listed as globs in the starter's `starter.json` (`projectOwned`: `project.json`, `figma.json`, the README, the lockfile, apps, explorations, …).

**Considered options:** a git remote and `git merge` from the starter (rejected: a repo made with "Use this template" shares no history with it, so the first merge conflicts on every file, and designers shouldn't have to resolve a repo-wide merge); copying the starter over the project and reading the diff (rejected: it silently undoes every local change, which is most of what a project is); recording a hash per core file, the way the add-on lock does (rejected: it tells changed from unchanged but can't combine the two, and the files that matter most, `CLAUDE.md` and `package.json`, are changed in every project); publishing the core as npm packages (rejected for the reason in `docs/adr/0001` and `0009`: it is source, scripts, skills and CI wiring that must live in the project).

**Consequences:** the first run has no recorded commit, so it guesses one: the newest starter commit at or before the project's first commit, since a generated repo starts with one fresh commit. That is a guess from a date. It is wrong when the template was generated from a branch or the first commit was rewritten, so the command says which commit it picked and how many core files match it exactly, and takes `--base <commit>` to overrule it. A merge is by lines, not meaning: two changes that don't touch the same lines combine cleanly and can still disagree, so the usual checks (`pnpm typecheck && pnpm lint && pnpm test`) run after an update; a merged `.json` file that no longer parses is treated as a conflict. The lock moves to the starter's latest even when some files were left for a person, so the `.starter-update` files are the to-do list and must not be deleted unread. Add-on text inside shared core files (the marked sections in `CLAUDE.md`, scripts in `package.json`) rides along with the merge: a project that removed an add-on keeps it removed unless the starter changed those same lines, which then shows up as a conflict. Updating is two commands, core then add-ons, and `starter.json` itself is core, so the list of project-owned paths updates too. A clone or fork of the starter shares its history and should pull instead; the command says so rather than guessing.

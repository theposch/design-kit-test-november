# Optional pieces are add-ons

The starter is copied once per engagement, so everything in it lands in every project whether that project uses it or not. Pieces only some projects need now live in a catalog, `add-ons/<name>/`, and a project takes them with `pnpm addon add <name>` and drops them with `pnpm addon remove <name>`. Each add-on is an `addon.json` in the shadcn registry-item shape (`name`, `title`, `description`, `files` with a `target`, `registryDependencies` for other add-ons) plus the files it copies in. What shadcn has no field for lives in its free-form `meta`: version and owner, keys merged into `package.json` files, and blocks of text inserted into shared files (CLAUDE.md, `.gitignore`, `pnpm-workspace.yaml`) between `addon:<name>` markers. `addons.lock.json` records what a project has installed, with a hash of every file copied in, so remove deletes only files nobody has changed. `pnpm addon check` validates the catalog, checks installed copies still match it, and runs a round trip on a scratch copy of the repo: every add-on out, nothing left behind, every add-on back, and the tree must be byte-identical.

**Considered options:** keeping everything in the starter and pruning per engagement (rejected: pruning is manual and easy to get wrong, and the starter only grows as people contribute); the shadcn CLI as-is (rejected: it copies files and installs packages but can't touch scripts, CI workflows or the agent guide, which is most of what our tools are); separate npm packages per tool (rejected: our tools are mostly scripts, skills and CI wiring that must live in the project, not behind an import).

**Consequences:** in this repo every installed add-on exists twice, as the catalog copy and the installed copy; `pnpm addon check` (run in CI) fails when they drift, so a change goes into both. Shared settings can't belong to an add-on: the Sites project slug moved from `explorations/sites.json` to `sites.json` at the root because the Storybook deploy needs it too, and turbo filters exclude explorations by package name (`!@explorations/*`) so they keep working when the folder is absent. Add-on scripts are appended to the end of a `scripts` block and add-on packages sorted into place, which is where a fresh add would put them. `pnpm addon update` brings a project's add-ons up to the starter's latest: files and `package.json` values nobody changed are replaced (the lock also records the values each add-on set, to tell), a changed file is kept with the new version beside it as `<file>.addon-update` for a person to merge, files deleted on purpose stay deleted, and each add-on's marked text is rewritten. Update always reads the catalog from the starter repo (the lock's `source`, or `--from <git url or folder>`), downloading only its `add-ons/` folder; the other commands read the local `add-ons/` folder when there is one, and the starter repo otherwise, so engagement repos can drop the folder.
